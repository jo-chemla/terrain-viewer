The app runs in the browser and has no server. The tile service is a small server that hands out what the app draws, so a map library, QGIS or a script can use a Terrain Viewer view without running the app. Two engines draw:

| Engine | Draws | Time per tile |
|---|---|---|
| **Direct** | Every 2D terrain mode and overlay (contours with labels, iso-line, mound detector, plane slicer, graticule, dark theme), computed in the server by the app's own code from any source the app reads, read with the app's own readers | 0.05 to 2.5 s |
| **Browser** | Everything: the app itself in a headless browser, so every source, every mode, imagery, 3D, split views and combined layouts | 3 to 10 s for a new block, then milliseconds |

Tiles and viewports take the direct engine whenever they can. 3D, tilted, rotated and split views always take the browser, and so do imagery and the few layers listed in [What goes to the browser](#what-goes-to-the-browser).

```bash
docker run -p 3400:3400 --shm-size=1g -v tv-tiles:/data/tiles ghcr.io/iconem/terrain-viewer-tiles
```

Then `http://localhost:3400/docs` is the reference below with a working **Test request** button, and `http://localhost:3400/openapi.json` its OpenAPI document.

## The two answers

| Address | Answers | Like |
|---|---|---|
| `/tiles/{z}/{x}/{y}.png` or `.jpg` | One Web Mercator tile by its index. 256 px; `{y}@2x` or `tilesize=512` for 512 px | An XYZ tile layer, titiler's `/tiles` |
| `/render.png` or `.jpg` | A picture of a viewport: `lat`, `lng`, `zoom`, or `bbox=west,south,east,north`, with `width` and `height`. Can be tilted (`viewMode=3d`, `pitch`, `bearing`) or split | A WMS GetMap |

A tile is the map alone. A viewport keeps the scale bar and the credits.

Both take the view as query parameters, the same words the [MCP server](/features/mcp-server) uses:

| Parameter | Meaning |
|---|---|
| `terrainSource` | An id from `/sources` (the built-in sources and the [library](/features/terrain-sources#the-library)), the address of Terrarium tiles, of a COG (`.tif`) or of a VRT (`.vrt`), or a configuration as JSON with the fields of a library entry: `{"url": "…/{z}/{x}/{y}.png", "type": "terrainrgb", "maxzoom": 15}` (types `terrarium`, `terrainrgb`, `cog`, `vrt`, `wms-raw`, `lerc`, `quantized-mesh`, `tilejson`) |
| `modes` | Comma-separated: `hillshade`, `colorRelief`, `contours`, `slope`, `aspect`, `curvature`, `tpi`, `roughness`, `lrm`, `svf`, `openness`, `localDominance`, `phong`, `matcap`, `shadows`, `moundDetector`, `isoline`, `graticules`, `planeSlicer`, `basemap` (also `tri`, `shapeIndex`, `blobness`, `eigenRatio`, `orientation`) |
| `imageryUrl`, `imagerySource`, `imageryDate` | Imagery under the terrain, drawn with the mode `basemap` |
| `engine` | `auto` (the default: direct when it can), `direct` (an error when it cannot), `browser` |
| anything else | Passed to the app as a [URL parameter](/dev/url-api): ramps, opacities, light direction, contour interval |

Every answer says which engine drew it in its `x-tv-engine` header, and `x-tv-engine-why` says why not the direct one.

## Names, not addresses

Like titiler's list of tile matrix sets, three lists give the ids the parameters take:

| Address | Lists |
|---|---|
| `/sources`, `/sources/{id}` | The 138 terrain sources: built-in and library, with type, tile address, zoom range, extent, and the engine that can draw each |
| `/colorramps`, `/colorramps/{id}` | The app's 268 colour ramps, to name as `colorRamp` (colour relief) or `slopeColorRamp` (slope); one ramp gives its stops |
| `/algorithms` | The modes with the engine that draws each |

A source that is not listed can still be given whole, as its address or as a JSON configuration.

## Contour lines as vector tiles

`/contours/{z}/{x}/{y}.pbf` answers the contour lines of a tile as a Mapbox Vector Tile, layer `contours`, each line with `ele` (its elevation in metres) and `level` (1 for a major line), the attributes of the app's own contour tiles. The client places the labels, where its map library wants them. `contourMinor` and `contourMajor` set the intervals (major lines only below zoom 6), `terrainSource` the source (any source the direct engine reads, see [Sources](#sources)).

```js
map.addSource("tv-contours", { type: "vector", tiles: ["http://localhost:3400/contours/{z}/{x}/{y}.pbf"], maxzoom: 15 })
map.addLayer({ id: "contour-lines", type: "line", source: "tv-contours", "source-layer": "contours", paint: { "line-width": ["match", ["get", "level"], 1, 1, 0.5] } })
map.addLayer({ id: "contour-labels", type: "symbol", source: "tv-contours", "source-layer": "contours", filter: ["==", ["get", "level"], 1], layout: { "symbol-placement": "line", "text-field": ["concat", ["get", "ele"], " m"], "text-size": 10 } })
```

```text
/tiles/{z}/{x}/{y}.png?modes=slope&terrainSource=custom-nl-ahn-dtm
/render.jpg?bbox=6.7,45.75,7.0,45.95&width=800&height=600&modes=hillshade,contours
```

In MapLibre:

```js
map.addSource("tv-slope", { type: "raster", tileSize: 256, tiles: ["http://localhost:3400/tiles/{z}/{x}/{y}.png?modes=slope"] })
```

## titiler's addresses

A client written for [titiler](https://developmentseed.org/titiler/) needs few changes: the service answers at the same addresses, for Web Mercator only.

| titiler | Here |
|---|---|
| `/tiles/WebMercatorQuad/{z}/{x}/{y}@2x.png` | The same tile as `/tiles/{z}/{x}/{y}@2x.png` |
| `/WebMercatorQuad/tilejson.json` | A TileJSON whose tile address keeps the parameters given; `tile_format`, `tile_scale` |
| `/bbox/{w},{s},{e},{n}/{width}x{height}.png` | `/render` with `bbox`, `width`, `height` |
| `url` | Read as `terrainSource` |
| `algorithm` | Read as one name of `modes` |
| `tilesize` | 256 or 512 |
| `rescale`, `colormap_name`, `bidx`, `expression`, `nodata`, other tile matrix sets | Not read. The app's own parameters set the ramps |

## What the direct engine draws

The direct engine computes the tile in the server, with no browser. It opens nothing: it rebuilds the map's layer stack from the same URL parameters the app would read, and computes every layer with the app's own code, bundled for Node.

| Layers | How |
|---|---|
| Colour relief, and the 14 computed modes: slope, aspect, TRI, curvature, TPI, LRM, roughness, shape index, blobness, eigen ratio, orientation, sky-view factor, openness, local dominance | The app's tile protocols (`lib/*-protocol.ts`), coloured with the paint the map computes (`lib/layer-paints.ts`, `lib/mode-relief.ts`) and interpolated between the ramp's stops as MapLibre does |
| Hillshade | MapLibre's two shader passes, rewritten in JavaScript line by line, fed with the paint the map computes: the five methods and the app's three multi-light presets |
| Matcap, Phong | The app's live GL layers, its default renderer: their fragment shaders rewritten in JavaScript (the normal of each pixel from the bilinear elevation, Phong's multiply and add passes over the layers below, the camera-relative matcap lookup). With `matcapRenderer=raster` or `phongRenderer=raster`, the app's tile protocols, as the app then draws them |
| Cast shadows | The app's tile protocol |
| Contours | maplibre-contour, the app's contour library, with its intervals, widths and colours; on the terrain, or on its local relief model with `contourReferenceMode=lrm`. The labels are drawn on the picture (elevation and "m" on major lines, bold 10 px with a halo, every 250 px along the line, upright, not on sharp bends or over another label), placed close to MapLibre's line symbols but not identically. The [vector tiles](#contour-lines-as-vector-tiles) carry `ele` for a client that places its own |
| Iso-line | At a value: the app's `isoband://` vector tiles over the chosen measure (elevation, slope, any computed mode or lighting), the fill and the line, and on slope the cliff teeth every 28 px. Every interval: the contour engine over the measure's tiles |
| Mound detector | The app's `tells://` vector tiles, a circle per candidate with the map's radius (fixed, or the measured diameter times `tellsScaleMultiplier`) and colours (outline, or coloured by blobness, plan curvature, Hessian or LRM) |
| Plane slicer | The colour relief the map draws for it, on the elevation or on the local relief model |
| Graticule | The lines at the app's spacing for the zoom, or `graticuleDensity`. Its labels sit on the edges of the screen in the app, so a tile has none |
| Dark theme | The black background, and the contour, label and graticule colours that follow the theme |

The layers stack in the map's order (the relief and lighting layers, then iso-line and graticule, mound markers, plane slicer, and the contours on top) over its white or black background, with the app's opacities. A colour ramp is read as MapLibre reads it: the stops rounded to the elevation encoding's step and the colours taken from an 8-bit texture. Every URL parameter the app reads for these layers applies: ramps, ranges, inversion, custom ramp stops, radii, light direction, exaggeration, opacities.

### Sources

The direct engine reads every source type the app reads, with the app's own readers. What a source's elevation tiles are (template, RGB packing, tile size, zoom range) comes from the function the map uses for its own decoders, `terrainTileSpec` in `lib/terrain-tile-spec.ts`, with the app's default settings (the in-browser COG reader on, Terrarium tiles, titiler at `titiler.xyz`). The readers are the app's protocols, registered in Node through the app's registry (`lib/protocol-registry.ts`) by `mcp/app-sources.ts`:

| Type | Read by |
|---|---|
| Terrarium, Terrain-RGB, custom RGB packing | The tiles fetched and decoded in the server |
| PMTiles | `pmtiles://`, Range reads of the archive |
| COG | `cog://` (geotiff.js), with the elevation colour function the map registers. A COG the in-browser reader refuses, or one pinned to titiler (`cogViaTitiler`, most of the library's), is read through titiler as in the app |
| VRT | `vrt://`: the VRT's own index, its files Range-read by geotiff.js and warped by proj4. Also GEM-15, Open Buildings and Meta's canopy height, whose indexes come from the deployed app. A VRT pinned to titiler goes through titiler |
| WMS, WCS, ArcGIS exportImage (`wms-raw`) | `float32dem://`, one Float32 GeoTIFF request per tile |
| LERC (ArcGIS tiled elevation, Esri World Elevation) | `lerc://`, Esri's wasm decoder |
| Quantized mesh | `quantized-mesh://`, the meshes rasterised |
| Difference (nDSM, change) | `demdiff://` over its two operands, each read as above |
| TileJSON | The manifest's tile template |

Not read in the server, so drawn by the browser: Mapbox, MapTiler and Cesium ion (they need an API key, which the service does not hold), STAC and MosaicJSON entries, a local file, a source whose address is not https, and a COG or VRT that does not answer. `/sources` gives each source its engine, and the reason when it is the browser.

### What goes to the browser

3D, tilted, rotated and split views (the camera is the app's); imagery and basemaps; building shadows (OpenStreetMap buildings); the sky and fog background; the historical mode; a source the server does not read (see [Sources](#sources)). The answer's `x-tv-engine-why` header names the reason.

What the remaining differences are:

- **† Dense contours at Matterhorn**: in this run the app gave up before its 1x tile was drawn (the browser picture is blank), so the line keeps the value of an earlier run of the same case on the same day.
- **Contour labels**: the lines are the same, from the same library and options; the labels are placed close to MapLibre's line symbols but not identically, its collision rules keep fewer of them on short wiggly lines (the local relief model), and the server's font is Liberation Sans where MapLibre draws its Noto glyphs. Without labels, 2.1.
- **Shape index**: in Paris, every difference is a pixel at exactly +1 (a dome), drawn transparent by the app and dark red by the direct engine. That is an app bug, fixed in this release (see the changelog): MapLibre rounds a ramp's stops to the elevation's encoding, so the last pair of a discrete ramp became one value and the shader divided 0 by 0. Once the fix is deployed both engines draw it dark red.
- **Iso-line cliff teeth** and **mound markers**: the same marks; the teeth start at a different offset along each line, and a few markers near a tile edge are missing on one side or the other.
- **Hillshade** on flat ground: the gradient is kept in 8 bits, as in MapLibre's own texture, and a tiny slope rounds one way or the other.
- **Matcap and Phong**: compared with the app's default live renderer, and with its raster renderer when `matcapRenderer=raster` or `phongRenderer=raster`.

Sources other than Mapterhorn compare the same way: a COG within 0.4 to 2.5, a VRT 0.2 to 0.8, a WMS 0.02 to 1.3, LERC 0.02 to 1.7, quantized mesh 0.01 to 0.5 (hillshade, colour relief and slope). Where a source has holes, the direct engine leaves them transparent while the map draws them at the fill height titiler gives them (0 m), so a GEM-15 hole or the ground under a building in a nDSM differs; the map's own source configuration and the decoders' will be one in the coming source schema.

`node mcp/compare-engines.mjs <service>` runs the comparison again and writes the table and, for each case, the two tiles side by side with their difference.

## How the browser draws a tile, and how fast

The browser engine does not compute a tile: the app draws it. For a tile, the app is opened on the 2048 px block that holds it (8 by 8 tiles of 256 px), the picture is cut into tiles, and all of them are kept a week on disk (`/data/tiles` in the image).

Measured on a laptop on 2026-11-21:

| | Time |
|---|---|
| Direct tile, one mode | 0.03 to 0.4 s once the elevation tiles are in memory; up to 2.5 s for local dominance or a first tile |
| Direct viewport, 900 by 600, three modes (MCP picture) | 1.8 s |
| Browser, first tile of a block, Chrome with a graphics card | 3 to 9 s |
| Browser, first tile of a block, in the container (no graphics card) | 10 s |
| Browser, its 63 neighbours, and any tile asked again within a week | under 0.1 s |
| Browser viewport, 600 by 400, 3D slope | 3 s |

An imagery tile from the browser engine equals the provider's own tile of the same index (mean difference 1.7 on 255, the JPEG compression), and joins its neighbour without a seam.

The browser engine suits a few views, a cache filled in advance, or pictures of 3D views for a report or an assistant; not a busy map. The direct engine can serve a live map.

## Settings

| Variable | Meaning | Default |
|---|---|---|
| `PORT` | The port | 3400 |
| `TV_BASE_URL` | The app to render | `https://terrain-viewer.iconem.com/` |
| `TILE_CACHE_DIR` | Where tiles and pictures are kept a week | `/data/tiles` in the image |
| `TV_RENDER_CONCURRENCY` | Pages rendered at the same time; each is a whole app | 2 |
| `TV_ALLOWED_HOSTS` | Host names accepted in the `Host` header, comma-separated | any |

The browser in the container reads any address given as a source: keep the service away from a private network, or behind a proxy that restricts who can call it. It has no sign-in.

The code is `mcp/tile-server.mjs`. The direct engine is `mcp/direct.mjs`, on the elevation reader `mcp/dem.mjs`, which the MCP server's `elevation` and `export_geotiff` tools use too. The browser engine is `mcp/render.mjs`, shared with the MCP server's pictures. Neither service imports the other. With `TV_RENDER_URL` set to the tile service's address, the MCP server asks it for its pictures in place of rendering them, which is how [`mcp/docker-compose.yml`](https://github.com/Iconem/terrain-viewer/blob/main/mcp/docker-compose.yml) wires the two. The MCP server's elevation tools need no browser any more, and its pictures of flat views are drawn by the direct engine in the server itself; only 3D, imagery and the other browser layers need a browser, its own or the tile service's.

Not yet run on a server.
