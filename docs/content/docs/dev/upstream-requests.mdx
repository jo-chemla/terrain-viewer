## MapLibre: renderToTerrainTile, the plan past experimental

A comment for PR 8588, short:

> Thanks for this, it is the hook we were missing. We build Terrain Viewer (terrain-viewer.iconem.com, MapLibre 6.13) and plan to use `renderToTerrainTile` for three things: draping Allmaps' warped old maps on terrain at any pitch, live Phong and Matcap shading computed in the custom layer (view-dependent, so `terrainTileRevision` bumps on every camera move), and cast shadows of buildings. Before we build on it: what is the plan for taking it out of experimental, and what might change? In particular whether per-tile calls could get the camera (for view-dependent terms), whether a revision bump on every frame is the intended way to drape something view-dependent or a `renderToTerrainTile` per frame is coming, and whether the clip-space convention (tile corners at ±1) and the `{ tileID, width, height }` arguments are settled. Happy to report back from a real use.

## Allmaps: WarpedMapLayer, pitch, globe and terrain

**WarpedMapLayer (MapLibre): render with MapLibre's projection, for pitch, globe and terrain**

`WarpedMapLayer.render()` rebuilds a flat `Viewport` from the four unprojected canvas corners, the centre, the scale and the bearing. With `map.getPitch() > 0` the warped map is drawn flat over the tilted view, in the wrong place (the README says pitch is unsupported), and on the globe projection it cannot follow the curvature.

MapLibre already hands a custom layer everything needed. In MapLibre 5 and 6, `render(gl, args)` receives `args.modelViewProjectionMatrix` and `args.defaultProjectionData` (the uniforms of MapLibre's own projection), plus `args.shaderData`: a `vertexShaderPrelude` exposing `projectTile()` and the `define`s of the current projection (Mercator or globe). Proposal: let the WebGL2 renderer take that, either a matrix (Web Mercator to clip space) as an alternative to `Viewport`, or better, MapLibre's prelude so the triangle vertices go through `projectTile()`. That gives pitch on Mercator and correct placement on the globe with one code path. Draping on terrain would follow once a custom layer can be rendered into MapLibre's terrain render-to-texture.

MapLibre 6.13 adds a simpler route for terrain ([#8588](https://github.com/maplibre/maplibre-gl-js/pull/8588), experimental): `renderToTerrainTile(gl, { tileID, width, height })` is called per terrain tile, in that tile's flat clip space, and MapLibre drapes the result. `WarpedMapLayer` could implement it by rendering a flat `Viewport` of each tile, which the renderer already supports; two things in `WebGL2Renderer` get in the way: `#renderInternal` sets `gl.viewport` to the canvas size, and the visible-tile fetching follows the last viewport rendered. Exposing a render-to-target call (viewport size and framebuffer as given) and keeping tile fetching tied to the main view would be enough.

Context: Terrain Viewer (MapLibre 6.13, `@allmaps/maplibre` 1.0.0-beta.44) shows Allmaps maps as overlays on 3D terrain. While the view is tilted we switch to `allmaps.xyz` tiles, which tilt and drape but are less sharp than the in-browser warp.

## Allmaps: plain images as a resource

**@allmaps/render: accept a plain image (or an `ImageBitmap`) as a map's resource, not only IIIF image services**

Terrain Viewer's Image Georeferencer places a plain image (a figure from a paper, a JPEG plan) from control points, with `@allmaps/transform`. MapLibre's image source draws from four corners only, so the bending fits (polynomial 2, thin-plate spline) cannot be shown correctly, while Allmaps' renderer already triangulates and warps on the GPU. A resource type for a single image (a URL or an `ImageBitmap`, width and height known, no tiles, no `info.json`) would let us hand our control points and transformation to `WarpedMapLayer.addGeoreferencedMap` and get every fit drawn exactly. The renderer accepts a `fetchFn`, so a synthetic level-0 IIIF service served from memory is a possible workaround today; a first-class resource would avoid it.

## Electrobun: per-variant update feed

**Updater: a feed name per variant, so two builds of one app can share a release**

The update feed is named after the channel (`stable-<platform>-update.json`, the archive next to it). Two variants of one app produce the same feed name, so they cannot share a `release.baseUrl`. Ours are a full build and a light build, with different `app.identifier`s. The archive already carries `app.name` (`stable-win-x64-TerrainViewerLight.tar.zst`), but `update.json` does not. Proposal: an optional `release.feedName` (or `app.name` / `app.identifier` in the feed file's name), used both by `electrobun build` and by `Updater.checkForUpdate`. Today we publish two GitHub releases, `desktop-latest` and `desktop-latest-light`.

## Planet: a browser OAuth client

**Insights Platform STAC (api.planet.com/x/data): a way for a browser app to get an access token**

The STAC API takes only an OpenID access token; a `PLAK` API key answers 401 there (it works on the Data API v1 and the tile service). The documentation says the Planet CLI and SDK are the only interactive OAuth clients for now, and that machine-to-machine tokens for `api.planet.com` are in progress. A web app can therefore only ask users to run `planet auth print-access-token` and paste the result, every two hours or so. Proposal, either: self-service registration of a public OAuth client (authorization code with PKCE, the app's own redirect URI), or accepting the API key on `/x/data` as the Data API v1 does. CORS on `/x/data` is already open, so nothing else is missing.

## Electrobun: the launcher's command line, handed to the app

A comment for [issue 483](https://github.com/blackboardsh/electrobun/issues/483) (argv passing on Linux and Windows; [issue 554](https://github.com/blackboardsh/electrobun/issues/554) reports the Linux drop separately), which asks for the same thing. The comment adds the Windows 2.0.2 confirmation, the workaround we ship and the PR offer:

Still the case on Windows with Electrobun 2.0.2: `launcher.exe` starts the Bun main process without its own arguments: a file dropped on the executable, a registered file type opened from Explorer, or `launcher.exe "C:\path\project.zip"` all reach `process.argv` as nothing. The main process has no supported way to learn what it was launched with. We read the launcher's command line ourselves through `ntdll` (`NtQueryInformationProcess` with `ProcessCommandLineInformation` on `ELECTROBUN_LAUNCHER_PID`, or the parent when it is `launcher.exe`) and split it with Windows quoting rules; it works but it is a reach into another process. Proposal: forward the launcher's arguments to the main process (as `process.argv` entries after the script, or an `ELECTROBUN_ARGS` JSON variable), and on macOS and Linux the same for `open -a` / `xdg-open` with a file, so one `Electroview`-side event ("open-file" with the paths) covers the three platforms. Happy to send a PR for the Windows part.

## geomatico: a height for no-data pixels in the terrain encoder

**renderTerrain: a configurable height for no-data pixels, or a nearest-valid fill, instead of 0 m**

Since [PR 51](https://github.com/geomatico/maplibre-cog-protocol/pull/51) (0.10.0) no-data pixels in a DEM are encoded as 0 m: `((isFinite(h) && !noData ? h : 0) + 10000) / 0.1`. That is right for a coastline, but a mountain DSM with holes (a drone survey, a lidar strip, a nodata collar around a rotated footprint) then shows a cliff dropping to sea level at every hole edge, and the hillshade draws black outlines along them. In Terrain Viewer we work around it by rewriting the tiles through our own protocol, which doubles the decode. Proposal: an option on the protocol, for example `cogProtocol({ terrainNoDataHeight })` or a URL fragment such as `#dem+nodata=-100`, with 0 as the default for compatibility; better still, a "nearest valid" fill so a hole takes the height of its edge. A fixed height already removes the walls for a per-file choice. Happy to send a PR for whichever form you prefer.

## maplibre-contour: a follow-up on issue 434

A comment on our own [issue 434](https://github.com/onthegomap/maplibre-contour/issues/434), with what we built since:

> Following up with what we ended up doing, in case it helps shape an API. Terrain Viewer (terrain-viewer.iconem.com) now routes every tile fetch of its derived modes through one registry, [`lib/protocol-registry.ts`](https://github.com/Iconem/terrain-viewer/blob/main/lib/protocol-registry.ts): `registerProtocol(scheme, handler)` registers with MapLibre and with the registry, and `fetchTileBitmap(url)` dispatches a `cog://`, `wms://`, `vrt://` or plain https URL to the right handler on the main thread. Contours go the same way: the DEM tile is fetched through the registry, decoded, and the elevation grid handed to the contour generation. So the piece needed from maplibre-contour is small: a `DemSource` option taking a function `(z, x, y, abort) => Promise<DemTile>` (or a raw Float32 grid) instead of a URL template, with the worker optional, since a custom protocol handler lives on the main thread and cannot be called from the contour worker. Happy to send a PR along those lines if that shape works for you.

## geomatico: bilinear upsampling from a coarser overview

A new issue (the nearest thread is [issue 14](https://github.com/geomatico/maplibre-cog-protocol/issues/14), closed in 2024, where the blur came from overview-level rounding):

**A bilinear option when a tile is served from a coarser overview**

When a z/x/y tile is requested past the finest level a COG holds, the reader fills the 256 px tile from a coarser level by nearest neighbour, so a terrain tile shows 2 x 2 or 4 x 4 blocks and the hillshade computed from it draws a staircase. Terrain Viewer (terrain-viewer.iconem.com) renders slope, aspect and hillshade from `cog://` DEMs, and the blocks show on every national DEM coarser than the view. Proposal: a `resampling` option on the protocol (`nearest` as today, `bilinear`, perhaps `cubic`), as a URL fragment (`#dem+resampling=bilinear`) or a `cogProtocol({ resampling })` setting, applied when the requested resolution is finer than the source level. For a DEM the interpolation belongs on the heights before encoding: interpolating the encoded RGB bytes would mix the channels. We work around it by requesting the parent tile and interpolating in our own protocol. Happy to send a PR.
