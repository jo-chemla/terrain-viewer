## MapLibre GL JS: a reply on issue 48

[Posted 2026-11-15](https://github.com/maplibre/maplibre-gl-js/issues/48#issuecomment-6894105178) under [birkskyum's mask example](https://github.com/maplibre/maplibre-gl-js/issues/48#issuecomment-6867399179) on [issue 48](https://github.com/maplibre/maplibre-gl-js/issues/48), after layer blending shipped in 6.18. The draft:

> Thanks, the fill sandwich is a neat trick, and thank you @CommanderStorm for landing this. Two notes from Terrain Viewer (terrain-viewer.iconem.com), which compares two imagery dates or two elevation models with a swipe and a blend.
>
> **World-space mask vs screen-space mask.** The fill gives a mask fixed to the ground. A swipe needs one fixed to the screen: the left half of the viewport, whatever the camera does. It can be approximated by rebuilding the fill's polygon on every `move` from `unproject()` of the screen rectangle, which holds from about zoom 3 up on a flat map, but breaks once the map is pitched towards the horizon or on the globe, where the screen rectangle does not map to a ground polygon. Since the layer already draws into its own framebuffer, would a screen-space clip be in scope: a per-layer scissor or stencil rectangle in viewport pixels (something like `raster-layer-clip: [x0, y0, x1, y1]` in normalized screen units)? It would also make side-by-side and lens comparisons possible inside one map, without a second canvas.
>
> **A `difference` mode.** For change detection the useful blend is `difference` (and `exclusion`): what did not change between two dates turns black and what did stands out. With the backdrop already sampled in the composite pass, |backdrop − layer| looks like one more case next to `multiply` and `screen`. Would a PR adding `difference` and `exclusion` (both W3C separable modes) be welcome?
>
> Today we keep two map canvases with CSS `clip-path` and `mix-blend-mode`, which works but leaves the blend out of the map canvas, so exports have to rebuild it by hand.

## Allmaps: plain images as a resource

[Posted 2026-11-15](https://github.com/allmaps/allmaps/issues/643#issuecomment-6894174249) as a comment on [issue 643](https://github.com/allmaps/allmaps/issues/643) (Allmaps rejects a level-0 IIIF service without tiles; Bert Spaan answered that the renderer wants tiles and suggested one `tiles` entry per size), the closest existing thread: no issue asked for a resource with no IIIF at all (searched 2026-11-15). The comment:

> Chiming in with a related use case, from the other end: no IIIF server at all.
>
> [Historical-Imagery](https://historical-satellite.iconem.com/) Image Georeferencer lets user set pair control points to estimate transform of a plain image (jpg, png etc), via [@allmaps/transform](https://docs.allmaps.org/packages/transform) - thanks for that utility in addition to all the great allmaps work!
>
> MapLibre's image source draws from four corners only, so the bending fits (polynomial 2, thin-plate spline) cannot be shown correctly. On the contrary, Allmaps' renderer already triangulates and warps on the GPU. The renderer accepts a `fetchFn`, so a synthetic level-0 IIIF service served from memory is a possible workaround today (with a single `tiles` entry covering the whole image, as suggested above).
>
> A first-class resource type for a single image would avoid the above workaround. This image could be a URL or an `ImageBitmap`, width and height known, no tiles, no `info.json`. It would let us hand our control points and transformation to `WarpedMapLayer.addGeoreferencedMap` and get every fit drawn exactly.

## Planet: a browser OAuth client

**Insights Platform STAC (api.planet.com/x/data): a way for a browser app to get an access token**

The STAC API takes only an OpenID access token; a `PLAK` API key answers 401 there (it works on the Data API v1 and the tile service). The documentation says the Planet CLI and SDK are the only interactive OAuth clients for now, and that machine-to-machine tokens for `api.planet.com` are in progress. A web app can therefore only ask users to run `planet auth print-access-token` and paste the result, every two hours or so. Proposal, either: self-service registration of a public OAuth client (authorization code with PKCE, the app's own redirect URI), or accepting the API key on `/x/data` as the Data API v1 does. CORS on `/x/data` is already open, so nothing else is missing. The self-service path is closed for us today: the personal account page has no OAuth section, and a workspace's Access tab shows "OAuth client limit reached. Creating OAuth clients is not available for your account" (checked 2026-10-15).

## maplibre-contour: a follow-up on issue 434

A comment on our own [issue 434](https://github.com/onthegomap/maplibre-contour/issues/434), with what we built since:

> Following up with what we ended up doing, in case it helps shape an API.
>
> **The problem, recap.** Terrain Viewer (terrain-viewer.iconem.com) reads elevation from many kinds of sources, most of them through custom protocols: `cog://`, `vrt://` (a mosaic of national LiDAR tiles), `lerc://`, `demdiff://` (the difference of two DEMs), `quantized-mesh://`, alongside plain Terrain-RGB and Terrarium URLs. A protocol handler registered with `addProtocol` lives on the main thread, so the contour worker cannot fetch those URLs.
>
> **What we built: two pieces.**
>
> 1. **One registry for every protocol**, [`lib/protocol-registry.ts`](https://github.com/Iconem/terrain-viewer/blob/main/lib/protocol-registry.ts):
>    - `registerProtocol(scheme, handler)` registers the handler with MapLibre *and* keeps it in a map.
>    - `fetchTileBitmap(url)` dispatches any URL, custom scheme or plain https, to the right handler and returns an `ImageBitmap`.
>    - So anything outside a MapLibre source (contours, export, elevation picker, profiles) can fetch a tile the same way MapLibre does.
> 2. **One resolver from any source to a tile template**, `useClientDemUpstream` ([`MapSources.tsx`](https://github.com/Iconem/terrain-viewer/blob/main/components/LayersAndSources/MapSources.tsx)):
>    - It turns any terrain source (built-in, custom URL, COG, VRT, LERC, TileJSON, a difference of two sources) into one template with its encoding and zoom range: `vrt://…`, `lerc://…`, `demdiff://…`, or the TileJSON's resolved tiles.
>    - Every derived mode (hillshade variants, slope, curvature, sky-view factor, contours) reads that template, so each works on every source type with no per-source code.
>
> **How contours use it.** The DEM tile is fetched on the main thread through the registry, decoded, and the elevation grid is handed to the contour generation.
>
> **What would help from maplibre-contour.** The piece needed is small:
>
> - a `DemSource` option taking a function `(z, x, y, abort) => Promise<DemTile>` (or a raw `Float32Array` grid) in place of a URL template;
> - the worker optional, since the fetch function lives on the main thread.
>
> Happy to send a PR along those lines if that shape works for you.

## Mapterhorn: a comment on issue 27

A comment on [issue 27](https://github.com/mapterhorn/mapterhorn/issues/27) (possible data sources; Wallonia and the Dutch orthophoto WMS were the last two suggestions):

> We keep a surveyed list of national elevation endpoints for Terrain Viewer, with the Mapterhorn resolution next to each: https://terrain-viewer.iconem.com/docs/features/national-datasets/. Three countries publish a finer national grid than the one ingested today, all as open services: Czechia (CUZK DMR 5G, 2 m against 5 m), the Netherlands (AHN DTM, 0.5 m against 5 m) and Norway (Kartverket NDH, 0.25 m against 1 m). The page also lists what a browser cannot consume but a pipeline might (Portugal and Sweden have open STAC indexes with the rasters behind auth), the regional sources finer than their national grid (Queensland's 0.5 to 1 m LiDAR mosaic among them), and the licence of each. Every row is a reproduced request, not a catalog entry. Mexico INEGI's 5 m MDE from my earlier comment is still download-only.

Before proposing a source there, check the project's [`EXCLUDED.md`](https://github.com/mapterhorn/mapterhorn/blob/main/source-catalog/EXCLUDED.md) and its licence rule (attribution-only, no change-the-terms-at-will clause, [wipfli's note](https://github.com/mapterhorn/mapterhorn/issues/27#issuecomment-6507782195)). Already declined and not to be asked again: Lithuania's 5 m DTM (non-commercial), the Azores (non-commercial) and Hong Kong (DATA.GOV.HK terms revocable at any time, which also rules out CEDD's 0.5 m 2020 LiDAR even though it is a free bulk download). The ❌ rows on [National Datasets](/features/national-datasets) fail the same test: Mexico INEGI, Indonesia DEMNAS, Haiti CNIGS, Klaipėda, Hawaii, South Australia's Murray and the Kīlauea 2018 survey.
