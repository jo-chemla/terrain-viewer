The repository keeps code and text. Anything heavy or regenerated goes to a GitHub release of [Iconem/terrain-viewer](https://github.com/Iconem/terrain-viewer/releases) instead, because a file committed once weighs on every clone for good. So the releases page is a file store with six kinds of content, only one of which is a software release in the usual sense.

Three patterns are at work. A **rolling** tag has a bare name (`ux-flows`, `demo-takes`, `docs-media`, `dataset-indexes`, `qgis-plugins-repository`) and its files are replaced or added to, so a link to it never goes stale and nothing that reads it needs editing. A **dated** tag (`slides-<date>`, `qgis-plugins-<date>`) is a snapshot never touched again; a new plugin version gets a new `qgis-plugins-<date>` release, and since 0.5.0 that release also holds the tile service bundles that version pins, so an installed plugin keeps downloading exactly what it was tested with. The desktop tags are the exception: `desktop-latest` and `desktop-latest-light` are rolling but keep their suffix, because the update feed address is inside every installed app, and `desktop-v<version>` is the permanent copy winget points at. A **content-addressed** store (`docs-media`) keeps every archive under its hash, and a lock file in the repository names the one a commit uses.

A release asset sends no CORS header, so a page cannot fetch one directly. Whatever the site itself has to read (the VRT indexes, the UX flows captures, the screenshots) is fetched into the build and served from the site's own origin. A video tag is not subject to CORS, which is why the demo videos play straight from the release.

## How the releases page is ordered

GitHub lists releases by the date of their tag, newest first, and offers no folders, no pinning and no way to hide one short of deleting it or turning it into a draft. A title can be changed freely; the order cannot. What does help: every title starts with its kind (**Desktop:**, **Data:**, **Media:**, **QGIS:**), set by the workflows and scripts that create the releases, so the list reads by family; only the current `desktop-v<version>` is kept, older ones are deleted once no winget manifest points at them; the **Latest** badge is set explicitly and belongs to `desktop-latest` (the desktop workflow sets it on every run, so create any other release with `--latest=false`), and everything that is not software is marked **pre-release**, which greys it in the list and keeps it out of the repository's sidebar.

## Docs screenshots

`docs/public/screenshots` is not tracked. `docs/media.lock` names the archive a commit uses (`screenshots-<sha256 prefix>.tar`, with its full hash, size and file count), and `scripts/docs-media.mjs` brings the folder in line with it:

```bash
pnpm docs:media        # download and unpack when the folder is not at the lock's version
pnpm docs:media:push   # pack the folder, upload it, rewrite docs/media.lock
node scripts/docs-media.mjs status
```

- **A fresh clone, another computer, CI**: nothing to do. `pnpm app`, `pnpm docs`, the docs build and the slide scripts pull first. The download is public, no login needed. A clone that predates the move sees the pictures deleted by its next `git pull` and gets them back the first time one of those commands runs.
- **After retaking or adding a screenshot**: `pnpm docs:media:push`, then commit `docs/media.lock` with the page that uses the picture. The push needs the `gh` CLI signed in with write access to Iconem/terrain-viewer. Until the lock is committed and pushed, every other machine and the deployed site keep the old pictures.
- **Do not leave a retake unpushed across a `git pull`**: when the lock changes under a folder, the pull replaces the folder with the lock's archive, and a local picture that was never pushed is gone.
- Old archives stay on the release, so an older commit still builds. The same release keeps `posted-on-twitter.zip`, the 13 pictures posted in 2025 that used to sit in the repository. The earlier versions of the pictures also remain in the git history: the move stops the growth, it does not shrink the past.

The archive is a tar, not a zip, for two reasons: the pictures are JPEG, PNG and MP4, already compressed, so a zip would save nothing; `tar` is on every machine the script runs on (Windows 10 and later, Git Bash, the CI runners) where `unzip` is not; and it unpacks with one command and no dependency. The name carries the archive's own hash, so two versions never collide.

## Dataset files

The VRT indexes and the coverage footprints work like the screenshots, file by file: `datasets.lock.json` at the root lists each file with its folder under `public/`, its size and its hash, and `scripts/dataset-assets.mjs` fetches what is missing or behind the lock. `pnpm app` runs it, and so does `pnpm build`, strictly, which is how the website and the desktop bundles get the files.

```bash
pnpm datasets                                      # fetch what is missing or behind the lock
pnpm datasets:push public/coverage/esri-3d.geojson # upload a rebuilt file, rewrite the lock
node scripts/dataset-assets.mjs status
```

An entry marked `"rolling": true` in the lock is not pinned to its hash: the monthly [coverage rebuild](/dev/coverage-footprints) replaces those files on the release without a commit (keeping each month as `<name>.<YYYY-MM>.geojson`, with a running `coverage-history.json`), a build takes whatever is there, and `pull --refresh` updates a local copy. A file changed locally and not yet pushed is never overwritten by a pull; the script says so and keeps it. A build fails when the release holds a file other than the one the lock names, so push and the lock commit go together.

## Adding a file to a release

```bash
# an index too large to commit: build it into public/vrt/, then
pnpm datasets:push public/vrt/<name>.vrt   # and commit datasets.lock.json
# a screencast
gh release upload demo-takes video/out/<take>.mp4 -R Iconem/terrain-viewer
# a new release that is not software
gh release create <tag> <files> -R Iconem/terrain-viewer --prerelease --latest=false --title "<Kind>: <what>"
```

The next deploy picks up anything in `datasets.lock.json` and on `ux-flows`; a file the site must serve from another tag needs a download step in `.github/workflows/deploy-gh-page-on-push.yml`.
