Almost everything this app draws beyond a plain tile server goes through a **custom protocol**: a URL scheme of our own, such as `slope://` or `vrt://`, whose tiles are produced by a JavaScript function instead of an HTTP request. This page explains the mechanism, lists every scheme, and describes the one rule that keeps them all reachable.

## What a custom protocol is

MapLibre GL JS lets an app claim a URL scheme with [`addProtocol`](https://maplibre.org/maplibre-gl-js/docs/API/functions/addProtocol/). Any source whose `tiles` template starts with that scheme then asks the registered function for each tile instead of fetching it:

```ts
maplibregl.addProtocol("slope", async (params, abortController) => {
  // params.url is the tile URL with {z}/{x}/{y} already filled in
  const bitmap = await computeSlopeTile(params.url, abortController.signal)
  return { data: bitmap } // image bytes, an ImageBitmap, or vector-tile bytes
})

map.addSource("slopeSource", { type: "raster", tiles: ["slope://<upstream>/{z}/{x}/{y}"], tileSize: 256 })
```

A few properties shape everything built on top:

- **It runs on the main thread.** MapLibre's worker asks the main thread for the tile, the handler runs there, and the result goes back to the worker. The [add a custom protocol example](https://maplibre.org/maplibre-gl-js/docs/examples/add-a-custom-protocol/) and the [PMTiles](https://docs.protomaps.com/pmtiles/maplibre) and [COG](https://github.com/geomatico/maplibre-cog-protocol) readers all work this way.
- **The source type decides what the handler returns.** A `raster` or `raster-dem` source wants an image (encoded bytes or an `ImageBitmap`); a `vector` source wants Mapbox Vector Tile bytes. This app's derived modes return bitmaps, see [Handing the tile back to MapLibre](/dev/terrain-analysis-pipeline#handing-the-tile-back-to-maplibre).
- **Each request holds a slot** in MapLibre's image-request queue for as long as the handler runs, which is why slow handlers can starve the basemap. See the stalled-tiles watchdog and `MAX_PARALLEL_IMAGE_REQUESTS` in `TerrainViewer.tsx`.
- **Only MapLibre's own sources get dispatched.** `fetch("slope://…")` from anywhere else fails with "URL scheme is not supported". That limit is what the registry below exists for.

## Every scheme this app registers

Three schemes come from libraries; the rest are ours, in two families: data-source protocols, which bring in data MapLibre cannot read on its own, and visualization mode protocols, which compute a view from that data.

### Third-party schemes

Registered through the same registry, but written by others:

| Scheme | What it serves | Project |
|---|---|---|
| `cog://` | Cloud-Optimized GeoTIFFs, read by range requests | [geomatico/maplibre-cog-protocol](https://github.com/geomatico/maplibre-cog-protocol), see [Terrain sources](/features/terrain-sources) |
| `pmtiles://` | Tiles packed in a PMTiles archive | [protomaps/PMTiles](https://docs.protomaps.com/pmtiles/maplibre), see [PMTiles and COG Contours](/dev/vendored-protocols) |
| `dem-contour://` | Contour vector tiles computed from a DEM | [onthegomap/maplibre-contour](https://github.com/onthegomap/maplibre-contour), registered by its own `setupMaplibre` and fed as described [below](#contours) |
| `tv-contour://` | The same contour vector tiles, computed inside MapLibre's workers (the default) | `lib/contour-worker-client.ts`, see [Contours](#contours) |

### Data-source protocols

Terrain sources, which read an elevation dataset MapLibre cannot read on its own and hand it back as Terrarium or Terrain-RGB tiles:

| Scheme | What it serves | Page |
|---|---|---|
| `float32dem://` | A WMS that returns float32 GeoTIFF elevation | [WMS Float32 DEM Protocol](/dev/wms-float32-protocol) |
| `vrt://` | A GDAL VRT mosaic of COGs in any CRS, reprojected with proj4 | [VRT Mosaic Protocol](/dev/vrt-protocol) |
| `gem15://dtm`, `gem15://dsm`, `openbuildings://<year>` | Google GEM-15 (15 m elevation, global) and Open Buildings 2.5D: thousands of per-cell COGs, each in its own UTM zone, which no single VRT can index. Not MapLibre protocols of their own: the URL stands where a VRT URL would, inside `vrt://`, which routes each tile to the cells it overlaps | [Cell-routed sources](/dev/cell-routed-sources) |
| `lerc://` | Esri LERC tiles from an ArcGIS ImageServer | [ArcGIS LERC Elevation Protocol](/dev/lerc-protocol) |
| `quantized-mesh://` | Cesium quantized-mesh terrain, rasterised | [Quantized Mesh Protocol](/dev/quantized-mesh-protocol) |
| `demdiff://` | The difference of two sources (an nDSM, a change layer) | [Derived Terrain Protocol](/dev/demdiff-protocol) |

Imagery sources, reading tiles MapLibre could not place, decode, request or clean up on its own:

| Scheme | What it serves | Notes |
|---|---|---|
| `epsg3395://` | Tiles cut in World Mercator (EPSG:3395, the ellipsoid), resampled onto Web Mercator rows in the browser. Yandex Satellite in the library is the one such provider; a plain XYZ source would sit up to a dozen kilometres off at mid latitudes | The two grids share their columns exactly, so each Web Mercator tile reads the one or two EPSG:3395 tiles of the same x and interpolates between rows (`lib/epsg3395-protocol.ts`). The historical-satellite app did this through titiler and a GDAL_WMS definition |
| `epsg4326://` | Tiles on the geographic WGS84 grid (origin -180, 90; level L is 180 / 2^L degrees a tile, 2 x 1 tiles at level 0), the grid of an ArcGIS cache in EPSG:4326 and of WMTS's WorldCRS84Quad. The Holmul DEM picture in the library is one; a hosted TilesOnly service has no `export` to ask for Web Mercator instead | Web Mercator zoom z reads level z - 1, where a 4326 tile has the Mercator tile's width and column x; rows are resampled by latitude as for 3395 (same file, `lib/epsg3395-protocol.ts`, registered in the app and the tile service) |
| `gtimelapse://` | Google Earth Timelapse's annual mosaics, 1984 to 2022, from the viewer's own video tiles: one VP9 WebM per tile with a frame per year, seeked in a video element and read as a bitmap | [Google Earth Timelapse](/dev/google-timelapse) |
| `pcmosaic://` | Landsat Collection 2 and Sentinel-2 L2A scenes mosaicked on the fly by Microsoft Planetary Computer: a STAC search (collection, window, cloud cover, least cloudy first) is registered with a POST, which a `tiles` template cannot send, then its tiles are fetched by search id | [On-the-fly mosaics](/dev/on-the-fly-mosaics) |
| `capture://` | One satellite pass drawn as one basemap: Maxar and Vantor cut a capture into a grid of COGs about 5 km across, NOAA a flight into frames, so each map tile asks titiler only for the 1 to 4 COGs it overlaps, among the ones the timeline's STAC search found | [On-the-fly mosaics](/dev/on-the-fly-mosaics#capture-mosaics-one-satellite-pass-from-many-cogs) |
| `planettile://` | Planet Monthly Mosaic tiles with the user's own key read at fetch time (so it is in no tile URL, style or cache entry), a local cache first, and a counter that stops fetching past a quota until the user allows more (`lib/planet-tiles.ts`) | [Historical imagery](/features/historical-imagery), [API keys](/features/api-keys) |
| `tiletx://` | A raster source's own fixes: `alphaMode` (`o=` 0 served, 1 opaque: any alpha to 255; 2 multiply: black, alpha 255 minus luminance; 3 screen: white, alpha luminance; no-data kept transparent) and `underzoom` (a tile below the service's minzoom assembled from its children, bounds-aware, at most 3 levels) | [Source schema](/dev/source-schema#the-record) |
| `unpaper://` | Paper removal for any tiled old map (Map Warper, Wikimaps, the national map series): pixels near the paper colour turn transparent, with Allmaps' smoothstep edge; `c=auto` detects the paper from a sample tile | [Remove paper](/features/basemaps#remove-paper) |

### Visualization mode protocols

Derived modes, which read any of the sources above (through the [one resolver](#one-resolver-for-every-consumer)) and compute something from it:

| Scheme | What it computes | Page |
|---|---|---|
| `slope://`, `aspect://`, `curvature://`, `tpi://`, `tri://`, `roughness://`, `blobness://` | Neighbourhood kernels over a padded elevation grid | [Terrain Analysis Rendering Pipeline](/dev/terrain-analysis-pipeline) |
| `lrm://` | Local Relief Model from an ancestor-tile low-pass | [LRM](/dev/lrm) |
| `svf://`, `openness://`, `local-dominance://` | Horizon searches over a wide neighbourhood | [Terrain Analysis Rendering Pipeline](/dev/terrain-analysis-pipeline) and [Tile Caches](/dev/tile-caches#why-svf-and-openness-feel-slower-than-the-other-derivatives) |
| `normals://`, `matcap://`, `phong://`, `shadow://` | Surface normals and the lighting built on them | [Lighting Effects](/dev/lighting-effects) |
| `tells://` | Mound and pit candidates, as vector tiles | [Visualization modes](/features/visualization-modes) |
| `cog-contour://` | Contours from a COG, computed in a worker | [PMTiles and COG Contours](/dev/vendored-protocols) |
| `threshold://` | Any DEM-shaped template (the terrain or a derived mode) cut at one value into a two-level raster, outlined by maplibre-contour or filled with a colour: an iso-slope at 30°, a sky-view factor at 0.8, a flood level at 312 m | [Iso-line](/features/visualization-modes#iso-line) |
| `luma://` | A colour tile (Phong, Matcap, the hard shadow) turned into a Terrarium luminance, so `threshold://` and `isoband://` can cut a lighting mode too (`lib/threshold-protocol.ts`) | [Iso-line](/features/visualization-modes#iso-line) |
| `isoband://` | The same "at a value" line as vector tiles: marching squares (d3-contour) on the padded measure tile, one geometry for the area and its outline, so the fill stops exactly on the line | [Iso-line](/features/visualization-modes#iso-line) |

## The registry

`lib/protocol-registry.ts` is the one place a scheme is registered, and the one way anything fetches a tile URL itself.

```ts
import { registerProtocol, fetchTileBitmap, dispatchTile } from "@/lib/protocol-registry"

// Registration (components/TerrainViewer.tsx, once at startup):
registerProtocol("vrt", withTileResultCache(vrtProtocol))
registerProtocol("slope", withTileResultCache(slopeProtocol))

// Consumption, anywhere in the app:
const bitmap = await fetchTileBitmap("vrt://…/15/8074/14743", signal) // custom scheme: its handler; http(s): fetch()
```

`registerProtocol` records the handler and passes it on to `maplibregl.addProtocol`. `dispatchTile` looks a URL's scheme up and calls its handler directly; `fetchTileBitmap` does that for our schemes and a plain `fetch()` for everything else. An unregistered custom scheme throws an error that names the registry, instead of the browser's generic one.

### Why it exists

MapLibre dispatches our schemes for its own sources only. Several parts of the app build a tile URL from a template and fetch it themselves:

- every derived mode reading its upstream (slope over a VRT asks for `vrt://` tiles),
- the GeoTIFF export and the 2D elevation picker and profile,
- the contours layer,
- the mound detector.

Before the registry each of them kept its own list of schemes to special-case, and every new protocol had to be added to every list. Twice one was missed: hillshade worked, because MapLibre fetched it, and every other mode drew nothing, first for `lerc://` and `quantized-mesh://`, then for `vrt://` and `demdiff://`. With the registry a consumer never needs to know which schemes exist, so a new source type works in every mode, in the export, in the picker and in the contours the day it is registered.

### The rule

**Register through `registerProtocol`, never `maplibregl.addProtocol` directly. Fetch a tile URL through `fetchTileBitmap` or `dispatchTile`, never `fetch()` directly.**

### One resolver for every consumer

The consumers also agree on *which* template to fetch. `useClientDemUpstream` (`components/LayersAndSources/MapSources.tsx`) turns a source id into the template the viz modes read: `vrt://…`, `lerc://…`, a difference's `demdiff://…`, a TileJSON's resolved tiles. The export and the 2D picker (`getClientExportSource` in `lib/client-export.ts`) and the contours layer fall back to it for every source type they have no direct path for. That is what makes the [feature matrix](https://github.com/Iconem/terrain-viewer/issues/16) green across all source types.

### Contours

Contours run inside MapLibre's own workers: `lib/contour-worker-client.ts` loads maplibre-contour and a small script into them with `importScriptInWorkers`, where it registers a `tv-contour://` protocol. The contour vector source asks for those URLs, MapLibre loads vector tiles in its workers, so the isolines and the vector-tile encoding run there. The worker reads a plain http(s) DEM tile itself and asks the main thread for any other scheme (a `tv-contour-tile` message, answered with `loadTileBitmap`, the loader every derived mode uses). MapLibre runs up to four workers (`setWorkerCount` in `src/main.tsx`), see [Tile Performance and Workers](/dev/performance).

The older path is still in the code but no longer reachable from the interface (the Contours in a Worker switch was removed on 2026-11-18): maplibre-contour's `DemSource` used directly. It fetches its DEM tiles itself, in a worker, with `fetch()`, so it cannot read our schemes. For a template on one of them (and for Local Relief Model contours, an `lrm://` template), `buildRegistryDemSource` in `components/LayersAndSources/ContoursLayer.tsx` builds a `DemSource` with `worker: false` and gives its manager two functions:

- a `getTile` that calls `dispatchTile` and returns the bitmap, and
- a `decodeImage` that draws the bitmap to an `OffscreenCanvas` and hands the pixels to maplibre-contour's own `decodeParsedImage`.

Isolines for these sources were then computed on the main thread, the price of the custom `getTile`. A remote COG with the client toggle on goes to the same worker a local COG file uses (`cog-contour://`) instead.

### Region reads

A tile handler answers one z/x/y at a time; an export wants one area at one size. Where a source can deliver that area directly, its scheme also registers a **region reader** (`registerRegionReader` in the registry, the readers in `lib/region-readers.ts`), and the export (`readRegionGrid` in `lib/client-export.ts`) uses it instead of a tile mosaic:

| Scheme | Region read |
|---|---|
| `float32dem://`, `float32dem-bbox://` (WMS) | One GetMap per 2048 px chunk of the area |
| `vrt://` | Each source file read once per 2048 px chunk, reprojected with the same approximate transformer as the tiles |
| `demdiff://` | The difference of its two operands' region reads, each through its own reader or tiles |
| everything else | A tile mosaic at the zoom that meets the export size |

The IGN LiDAR nDSM, a difference of two WMS layers, exports in two GetMap requests instead of a tile mosaic of each operand. COGs already had their own windowed read. A reader returns floats with NaN for nodata; on the export's EPSG:3857 grid, so they go straight into the file.

## Outside the browser: a rendering service

Not built. A note on how close the pieces are.

A protocol URL already says everything about one rendering: the mode, its parameters, the source underneath, and z/x/y. That is the shape of a [TiTiler](https://developmentseed.org/titiler/) request, with the difference that TiTiler computes on a server and this app computes in the page. A middleware that took the same URLs and answered with the bytes would serve the relief modes to clients that cannot run them: QGIS, a notebook, another web map, a report generator.

Two outputs make sense:

- **Tiles**: `GET /tiles/{scheme}/{z}/{x}/{y}.png?<the protocol's own parameters>`, the bitmap the handler returns. Any XYZ client reads it.
- **Viewport images**: one picture of a bounding box at a pixel size, for a figure or a preview, through the [region readers](#region-reads) and the mode's own compute rather than a mosaic of tiles.

What makes this plausible now and not before is the [speed pass of November 2026](/dev/performance): most modes cost 2 to 13 ms a tile, Sky View Factor and Openness about 100 ms where they cost a second. A server answering a screenful of tiles is no longer a queue of seconds.

What exists:

- The handlers, all behind one registry (`dispatchTile`), with a shared result cache.
- A first server that renders the app: the [MCP server](/features/mcp-server) drives a headless Chrome and returns a picture of any view in a few seconds. It is a viewport image service already, by the slow road (a whole page per picture).
- `tile-server/app-lib.ts` bundles part of the app's code for Node, which shows the catalog and source code runs there.

What is missing:

- The handlers lean on browser APIs: `createImageBitmap`, `OffscreenCanvas`, WebGL2 for the normal-based modes, web workers. On a server each needs a stand-in (a Node canvas, a headless GL, worker threads), or the service keeps one headless page open and calls `dispatchTile` inside it, which needs no port at all and is the quickest thing to try.
- Encoding to PNG or WebP on the way out, cache headers, and a disk or object-store cache in front, as a tile server has.
- Limits: a public endpoint that computes Sky View Factor on demand needs rate limits and a cap on the upstream sources it will fetch.

## Writing a new one

1. Write the handler in `lib/<name>-protocol.ts`. Return a bitmap through `toTileImage` (`lib/tile-image.ts`), or MVT bytes for a vector source.
2. Honour the abort signal, and throw on failure. A thrown error is not cached and MapLibre asks again later. A tile that silently comes back empty is cached for the session, which is how the VRT reader used to leave permanent holes after a timed-out range read.
3. Mark nodata with alpha 254, not 0. See [Derived Terrain Protocol](/dev/demdiff-protocol).
4. Register it in `TerrainViewer.tsx` with `registerProtocol`, wrapped in `withTileResultCache` unless it has its own caching. See [Tile Caches](/dev/tile-caches#wrapping-a-protocol).
5. If it is a terrain source, make `useClientDemUpstream` resolve the new source type to its template. Every consumer then picks it up.
