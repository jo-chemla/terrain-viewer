### With winget (Windows)

```powershell
winget install terrain-viewer
```

`terrain-viewer` is the package's moniker; its full identifier is `Iconem.TerrainViewer` (`winget install --id Iconem.TerrainViewer`). It runs the Installer of the full build (documentation inside) from the permanent `desktop-v<version>` release, per user and without admin rights; the app then keeps itself up to date like any other install. This works once the package is accepted into winget's community repository: the submission, [microsoft/winget-pkgs#469738](https://github.com/microsoft/winget-pkgs/pull/469738) (version 2026.11.14), passed the automated validation and was waiting for a moderator's review on 2026-11-25. Until it is merged, winget answers that no package matches: use the release above.

The desktop app is the same Vite build as the website, shown in the operating system's own webview (WebView2 on Windows, WKWebView on macOS, WebKitGTK on Linux) by [Electrobun](https://framework.blackboard.sh/electrobun/). No Chromium is bundled, so a build without the documentation is about 40 MB. The point is working offline on local data: a COG picked from disk opens through the app's own file picker and every mode runs in the webview; online sources (Mapterhorn, basemaps, WMS services) still need the network. It is an experiment: unsigned, built by the `Desktop bundles` GitHub workflow, on demand only since 2026-10-03 (the weekly schedule and the macOS and Linux jobs are paused to save Actions minutes, so bundles are built locally for now; every platform's last bundle stays on the release), and attached to the rolling [`desktop-latest`](https://github.com/Iconem/terrain-viewer/releases/tag/desktop-latest) release, which is replaced on every run. Each platform comes in two files, `TerrainViewer-with-offline-docs-v<date>-Setup-<platform>` (the documentation bundled for offline reading, about 220 MB) and `TerrainViewer-light-online-docs-v<date>-Setup-<platform>` (about 40 MB, its Documentation button opens this website); Windows and Linux also get a `...-Portable-<platform>.zip` that runs without installing. The date is the build day. Sources live in `desktop/` of the repository.


## On a phone or tablet: add to the home screen

The website installs as an app on a phone or a tablet, no store and no download: on Android, Chrome's menu then **Add to Home screen** (or **Install app**); on iPhone and iPad, Safari's share sheet then **Add to Home Screen**. The icon opens the app full screen, without the browser's bars, on the same URL state as the website. Nothing is cached for offline use: it is the website in its own window, which is what keeps it from ever being out of date. terrain-viewer.iconem.com installs as Terrain Viewer with the mountain icon, historical-satellite.iconem.com as Historical Sat with the clock.

## Installing or running on Windows and Linux

On Windows the Setup file is one self-contained `.exe` (the payload is appended to Electrobun's installer stub, the layout its Linux installer uses; Hutch itself only writes a zip with a hidden `.installer` folder beside the exe). It installs under `%LOCALAPPDATA%\com.iconem.terrain-viewer` (`-light` for the light build, so both can be installed) and adds a Start menu entry; the light build's shortcuts are named "Terrain Viewer Light" so the two installs do not overwrite each other's. Links the app opens in a new tab (the documentation, GitHub, data providers) go to the system browser: the page sends them to the main process over the host channel, because on Windows Electrobun's WebView2 wrapper has no new-window handler and a plain `window.open` would pop WebView2's own bare window. On Linux the Setup is a self-extracting tar.gz.

On Windows, `winget install terrain-viewer` ([once the package is merged](#with-winget-windows)) or the Installer on the release adds a Start Menu entry, per user and with no admin rights. Each build also stays on a permanent `desktop-v<version>` release. A Planet key does not ship with the app: paste your own in Settings for the monthly mosaics.

The Portable zip needs no installation: unzip it anywhere and start `Terrain Viewer.cmd` (Windows) or `./terrain-viewer` (Linux); the program itself is `bin/launcher`, which has to stay next to `Resources/`. Nothing is written outside the folder except the webview's own profile.

## Command line

`launcher.exe` takes two kinds of argument, alone or together. It lives at `%LOCALAPPDATA%\com.iconem.terrain-viewer\stable\app\bin\launcher.exe` (`com.iconem.terrain-viewer-light` for the light build); in the Portable folder it is `bin\launcher.exe`.

A query string, or a full link whose query is taken, opens the app on that state, the way the link opens the website. Everything the [URL API](/dev/url-api) offers works: camera, sources, modes, projects, drawings and bookmarks by URL. Quote it, since `&` means something to the shell:

```bat
launcher.exe "?lat=45.92&lng=7.03&zoom=11&viewMode=3d"
```

A path to a `.json` or `.zip` file imports it, the way **Import** in General Settings does ([Projects](/features/advanced/projects)): a project export (plain JSON, or a zip with bundled local COGs), or a plain list of sources, added to the custom terrain and basemap lists. The list is either `{ "customTerrainSources": [...], "customBasemapSources": [...] }` (the shape of a project export's sources and of Save Project Preset's snippet) or one array whose entries carry `"kind": "terrain"` or `"kind": "basemap"` (it may be left out when the type belongs to one list only, `terrarium` or `tms` for instance, but not for `cog`, `cog-local` or `tilejson`); each entry needs a `url` and a `type`. The app opens, imports the file, reloads once and says so in a toast. Give a full path, since the launcher starts the app from its own `bin` folder and would read a relative path from there:

```bat
launcher.exe "C:\Users\me\Documents\alps-project.zip"
```

With both arguments, the project's own view wins where the two set the same parameter. There is no size limit: the page reads the file as bytes, as the Import button does. For the duration of the import the file is linked (or copied, when it sits on another drive) into the app's own folder, `Resources\app\views\app\open\` next to the web build, where the page can read it, and removed once read. A missing or unreadable file gets a toast saying so.

## Local tile service

The desktop app can run the [tile service](/dev/tile-service) on this computer, for the [QGIS plugin](/dev/qgis-plugin) and any other map client that reads XYZ tiles: **Settings > Desktop: local tile service** (a section shown in the desktop app only, never on the website). Off by default.

- **Run the tile service on this computer** starts it, on `http://localhost:3400`; turning it off stops it. The setting is kept by the app (`tile-service.json` next to `updater.log`), so a service left on starts again at the next launch. **Port** (1024 to 65535, **Apply**) moves it, restarting it if it runs; **Default (3400)** brings it back.
- The status line says starting, running (with the address and the process id), or why it stopped: a port already answered by another Terrain Viewer tile service (one started by hand: QGIS can use it as it is), a port taken by another program, or the service exiting (a toast too; its log, `tile-service.log` next to the setting, is named).
- A dot before the status is green while the service runs, amber while it starts or stops, red when it stopped on an error, grey when off. Under it: the **Endpoint** (`http://localhost:<port>`) with a copy button, a link to the service's **API reference** (`http://localhost:<port>/docs`, its Scalar page, once it runs), and a **Quick start** list of addresses to copy (a sub-section of its own, open by default, which remembers being folded), built from the port: slope XYZ tiles from Mapterhorn, sky-view factor XYZ tiles from the IGN LiDAR HD DTM (France), Mapterhorn's quantized-mesh `layer.json` for CesiumJS or a Blender terrain add-on, and Esri Wayback imagery of 2020. The list is `lib/tile-service-quickstart.ts`, also exported to the service (`tile-server/app-lib.ts`) so its docs page can show the same addresses.
- **Fold all / Expand all** at the top of Settings folds this section with the others.
- It listens on `127.0.0.1` only (nothing on the network, no firewall prompt), reads no `.env`, and stops with the app, even after a crash (it stops when its standard input, a pipe from the app, closes).
- **NASA Earthdata token** (G-LiHT's protected DTM, DSM and CHM files, through the service's [`/proxy/earthdata`](/dev/tile-service#cors-proxy-for-nasa-g-liht)): the service takes `EARTHDATA_TOKEN` from the app's environment (a user environment variable, set before the app starts). Without it, it reads the line `EARTHDATA_TOKEN=<token>` of `tile-service.env`, a text file you create next to `tile-service.json` (`%LOCALAPPDATA%\com.iconem.terrain-viewer\stable\tile-service.env` for the installed full build on Windows, `com.iconem.terrain-viewer-light` for the light build, the folder above `bin` for a Portable or winget copy). Only that line is read, at each request, so a token written there works without restarting anything; the environment variable wins when both are set. The token stays in the service: it never reaches the page, a status line or a tile address. Generate one at [urs.earthdata.nasa.gov](https://urs.earthdata.nasa.gov) (**Generate Token**); it lasts 60 days.
- Flat, north-up tiles only (the direct engine: Node and sharp; no browser engine, so 3D, tilted or split views answer 501). The elevation still comes from the online sources.

**With QGIS**: install the Terrain Viewer QGIS plugin (the plain zip is enough), turn the setting on here, then in QGIS open the Terrain Viewer panel (Web toolbar), keep the address `http://localhost:3400` (or the port picked here) and press **Connect**. If the app is closed or the setting off, the panel warns that the service does not answer and suggests starting the desktop app with its tile service on.

How it runs: the build ships the service in `Resources/app/tile-service/` (Node 22, the service, its node_modules with the platform's sharp: the same folder as the tile service bundle the QGIS plugin installs from its panel, staged by `ci-bundle.sh` with `qgis-plugin/make_zip.py --server-dir`), about 30 MB more in the installers. The main process (`desktop/src/bun/tile-service.ts`) starts that Node as a child process. Not inside the main process: Cottontail loads sharp and runs the service, but drew a slope tile in 57 s where Node takes 5 (2026-11-25), and a crash there would take the window along.

## Updates

Two rolling releases, one per build: `desktop-latest` holds the full build (installers, portable zips and its updater feed), `desktop-latest-light` the light build's. Electrobun names the feed after the channel (`stable-<platform>-update.json`), so the two builds cannot share one release. Both check their feed at every launch and then every hour while the app is open (before 2026-11-25 only at launch, so an app left open said "up to date" while newer builds came out). The full build, in detail: `stable-<platform>-update.json` and the matching `.tar.zst` are uploaded next to the installers, and Electrobun's updater (`release.baseUrl` in the generated config) downloads a newer build in the background. An **Update available** toast stays up during the download with a progress bar, the percentage and the time left (a spinner until the first percentage), until the download ends or its × dismisses it; then an **Update downloaded** toast offers **Restart and install**, and otherwise the build installs at the following launch, quitting and relaunching through its update helper, which takes about half a minute. The About section shows the updater's state under the version line: checking, up to date with the time of the check, downloading with its percentage and time left, downloaded and waiting for the next launch, installing, installed at this launch. A newer build is named by its day and commit (`2026.11.25 (2ba6460)`), taken from the release notes. Every step is also logged to `updater.log` next to the `app` folder (`%LOCALAPPDATA%\com.iconem.terrain-viewer\stable` on Windows). Builds made before 2026-10-02 have no feed address baked in and never update: install the current one once. The About section at the bottom of the sidebar shows the build day and commit; in the desktop app only (the website shows just the version), its **Is this the latest version?** link (which also has the updater check its feed, and bypasses the browser cache) compares that commit with the newest commit on `main` and with the commit the `desktop-latest` (or `desktop-latest-light`) bundles were built from, and links the release page; when the bundles come from another commit it says what the updater is doing about it (fetching it, downloaded, or a feed that does not list it yet while a build is being published). The desktop app also gets two buttons there: **Check for updates** checks the feed at once and downloads a newer build without installing it, and **Restart and install** shows while a downloaded update waits, so a missed **Restart now** toast is not the only way to install it before the next launch (a copy installed by winget or unzipped from a Portable zip answers that it updates the way it was installed). The light build compares with the `desktop-latest-light` release, whose feed it reads. The app version is the build day (`2026.11.25`), so two builds made the same day show the same version: the commit in the About line tells them apart, and the updater compares bundle hashes, not versions. The Portable folder is replaced by downloading it again, the updater never touches it (it only knows the installed copy).

The window title is the app's name per build: "Terrain Viewer", or "Terrain Viewer Light" for the light build, as its installer and shortcuts are named (read from the bundle's `version.json`, `displayName`).

A copy installed by winget or unzipped from a Portable zip does not update itself: Electrobun's updater only works on an app in `%LOCALAPPDATA%\<identifier>\<channel>`, where the Setup installs it. Such a copy skips the check at launch; `winget upgrade Iconem.TerrainViewer` updates it once the new version is in winget-pkgs.

## Opening the macOS build

The app is not notarized by Apple: it is only ad-hoc signed on the build runner, with no Apple Developer ID. Two files install it, the `.pkg` first.

### The installer package (`.pkg`, recommended)

`TerrainViewer-with-offline-docs-v<date>-Installer-macos-arm64.pkg` (or `TerrainViewer-light-online-docs-...` for the light build) installs the app into the Applications folder.

1. Double-click the `.pkg`. macOS blocks it once ("Apple could not verify ... is free of malware"): click **Done**.
2. Open **System Settings > Privacy & Security**, scroll to Security, and click **Open Anyway** next to the package's name; confirm with your password or Touch ID, then **Open**.
3. Follow the installer. The app lands in Applications and opens normally from there or from Launchpad, with no further warning: what the installer writes carries no download quarantine.

Do this once per new version you download; the app's own updates (see [Updates](#updates)) need nothing.

### The disk image (`.dmg`)

The `.dmg` opens on the usual drag-to-install window: the app on the left, a shortcut to the Applications folder on the right, an arrow between them. Drag the app onto Applications and eject the disk image. A dragged app keeps the download quarantine flag, and macOS refuses an ad-hoc signed app that carries it, so clear the flag once in Terminal before opening it:

```bash
xattr -cr "/Applications/Terrain Viewer.app"
```

(`"/Applications/Terrain Viewer Light.app"` for the light build.) Then start it from Applications or Launchpad.

### How the build makes them

Electrobun leaves the `.app` with a broken signature (its binaries are only linker-signed), which macOS reports as "damaged". `desktop/ci-bundle.sh` signs it ad hoc (`codesign --force --deep --sign -`, then `codesign --verify --deep --strict`), remakes the `.dmg` around the signed app, and builds the `.pkg` with `pkgbuild`, marked not relocatable (`BundleIsRelocatable` set to `NO` in the component plist: otherwise Installer updates a copy of the app it finds elsewhere, in Downloads or on a mounted disk image, instead of writing to Applications). The workflow then installs each `.pkg` from a copy carrying the quarantine flag, as a browser download would, and fails if the installed app carries `com.apple.quarantine`. The updater feed is untouched by the signature: the `.app` is Electrobun's self-extractor, which unpacks its payload (the same `.tar.zst` as the feed) on first launch, and the hash the updater compares is the payload's, written at build time.

### Signing and notarizing later

With an Apple Developer ID (the Apple Developer Program, 99 USD a year), the warning goes away. What it would take, not wired yet:

- Repository secrets: `APPLE_CERTIFICATE` (the "Developer ID Application" certificate and its key exported as a `.p12`, base64), `APPLE_CERTIFICATE_PASSWORD` (the `.p12`'s password), `APPLE_SIGNING_IDENTITY` (`Developer ID Application: <Name> (<TEAMID>)`), `APPLE_ID` (the Apple account's email), `APPLE_APP_SPECIFIC_PASSWORD` (an app-specific password from account.apple.com) and `APPLE_TEAM_ID`.
- In the macOS job, before the bundle step: import the `.p12` into a temporary keychain (`security create-keychain`, `security import ... -T /usr/bin/codesign`, `security set-key-partition-list`).
- In `desktop/ci-bundle.sh`, sign with that identity instead of the ad-hoc `-`: `codesign --force --deep --options runtime --timestamp --sign "$APPLE_SIGNING_IDENTITY" "$app"` (the hardened runtime is required for notarization; WKWebView needs no extra entitlement), build the dmg, sign it too, then `xcrun notarytool submit TerrainViewer.dmg --apple-id "$APPLE_ID" --password "$APPLE_APP_SPECIFIC_PASSWORD" --team-id "$APPLE_TEAM_ID" --wait` and `xcrun stapler staple TerrainViewer.dmg`.
- Electrobun's own path is `mac: { codesign: true, notarize: true }` in `desktop/gen-config.mjs` with `ELECTROBUN_DEVELOPER_ID`, `ELECTROBUN_APPLEID`, `ELECTROBUN_APPLEIDPASS` and `ELECTROBUN_TEAMID` in the environment (the names of Electrobun's code-signing guide: check them against the pinned version); `ci-bundle.sh` would then skip its ad-hoc signature and keep only the dmg layout step.

Windows shows a SmartScreen warning for the same reason: More info, then Run anyway.

## The pieces

| File | What it is |
|---|---|
| **Hutch** | Electrobun's command-line tool (`hutch electrobun build`, `hutch electrobun dev`). It installs the Electrobun *devkit* for the version pinned in `desktop/hutch.config.ts` (2.0.2) into `desktop/.hutch/`, the way `rustup` or `corepack` pin a toolchain, and drives the build. It is Electrobun's own CLI since v2, not a fork. |
| **`cottontail.exe`** | The main-process runtime. Electrobun 2 runs the main process (the TypeScript in `desktop/src/bun/index.ts`, which opens the window) on *Cottontail*, its own trimmed Bun-derived runtime, instead of a full Bun binary: `mainProcess: "cottontail"` in `electrobun.config.ts`. |
| **`launcher.exe`** | The small native bootstrap the shortcut points at. It locates the current app version (the updater can install a newer one next to it), starts Cottontail with the main script, and hosts the native window / webview through `ElectrobunCore.dll`. |
| **`bspatch.exe`, `zig-zstd.exe`** | The updater's tools: apply delta patches, decompress `.tar.zst` update archives. |
| `Resources/app/views/app/` | The Vite `dist/`, served to the webview under the `views://app/` scheme. |
| `Resources/app/tile-service/` | The [local tile service](#local-tile-service): `bin/node(.exe)`, `server.mjs` and its node_modules, started on demand by the main process. |

## What a build writes

Hutch writes next to `electrobun.config.ts` (i.e. in `desktop/`), never into the app's `dist/`:

```text
desktop/build/stable-win-x64/
  TerrainViewer/                      the application folder - runs as is
    bin/launcher.exe                  start here
    bin/cottontail.exe, ElectrobunCore.dll, ...
    Resources/app/views/app/          the web build
  Terrain Viewer-Setup.exe            installer
  stable-win-x64-TerrainViewer.tar.zst, stable-win-x64-update.json   updater feed
desktop/artifacts/
  win-x64-TerrainViewer-Setup.zip     what the workflow uploads
  terrain-viewer-portable-windows-x64.zip   the application folder, zipped (workflow step)
```

macOS gets `TerrainViewer.app`, an Installer `.pkg` and a `.dmg` (laid out by `desktop/dmg-settings.py` with [dmgbuild](https://dmgbuild.readthedocs.io): the app, an Applications link and an arrow), Linux a folder and a self-extracting `.tar.gz`.

## Portable: no installer

Electrobun does not produce a single-file executable: the webview host, the runtime and the web build are separate files by design (the updater patches them individually). The portable form is the application folder itself. The workflow zips it as `terrain-viewer-portable-<platform>.zip`: unpack anywhere, run `bin/launcher.exe` (`TerrainViewer.app` on macOS, `bin/launcher` on Linux). Nothing is written to the registry or to `Program Files`; the app's own data (the browser storage of the webview) goes to the user profile as any WebView2 app's does.

Building locally:

```bash
pnpm install && pnpm build                 # dist/
pnpm --dir docs install && pnpm run docs:build && mkdir -p dist/docs && cp -r docs/out/. dist/docs/   # optional: bundle the docs
cd desktop
node gen-config.mjs                        # electrobun.config.ts from dist/
hutch install                              # devkit, once
hutch electrobun build --env=stable
```

Two Windows gotchas, both in `desktop/README.md`: build from a plain folder (a git worktree path fails with `AccessDenied`), and from PowerShell rather than Git Bash (the release step runs `tar`; GNU tar fails, Windows' bsdtar works).

## Icon

`desktop/icons/` is `public/favicon.svg` rasterised: `icon.ico` (16 to 256 px) for the installer, the shortcut and the taskbar, `icon.iconset/` for the `.app` (converted with `iconutil` on the macOS runner), `icon.png` (512 px) for the Linux desktop entry. `gen-config.mjs` sets `build.win.icon`, `build.mac.icons` and `build.linux.icon`. Hutch embeds the `.ico` into `launcher.exe`, `cottontail.exe` and the setup executable.

## Docs and external links

When `dist/docs/index.html` exists (the workflow merges the Next.js export there, as the Pages deploy does), `gen-config.mjs` bundles the docs and the sidebar's Documentation button resolves to `views://app/docs/` offline. The main process handles `new-window-open` (links with `target="_blank"`): a `views://` URL opens in a second window, an `http(s)` one in the system browser. Unverified so far: whether the `views://` handler serves `index.html` for a directory URL (the docs export uses trailing-slash URLs); the fallback would be serving the docs from a local port.

## Fullscreen

The map's fullscreen button uses the browser Fullscreen API on the map container. Inside WebView2 or WKWebView the element fills the webview; whether the native window frame goes away as well has not been checked. Electrobun's `BrowserWindow.setFullScreen()` is there if it does not, wired from the main process.
