Experimental: rendering NASA LRO **LOLA** (Lunar Orbiter Laser Altimeter) terrain in
terrain-viewer, the same data behind Casey Handmer's Cesium south-pole flyovers — but
streamed as Cloud-Optimized GeoTIFFs through the existing [BYOD](/features/byod)
`cog://…#dem` custom terrain source, so every relief mode (hillshade, slope, SVF,
[sun-position shadows](/features/sun-position) over permanently shadowed craters)
relights it live in the browser. No app-code changes were needed; only the data had
to be repackaged (see the pipeline notes below).

## Coverage vs. resolution

LOLA's orbit tracks converge at the poles, so gridded resolution improves toward
90°S — NASA publishes **nested polar caps**, not one full-res global file. What
exists, where:

## Kaguya TC stereo DTM coverage

are **not** sparse: 155,925 stereo strips (~10 m/px, CORS-served COGs) blanket the
entire Moon — the emptiest 15°×15° cell still holds 289 strips. Strips per cell,
counted live from the USGS STAC API (August 2026; hover any cell; thin lines mark

## The three mercator tricks

MapLibre only speaks Web Mercator, which neither exists on the Moon nor reaches
past **85.051°** latitude — so lunar DEMs get one of three treatments:

- **Metric fake-geo** — the PGDA caps are south polar stereographic *in meters*;
  `gdal_translate -a_srs EPSG:3857` relabels those meters as mercator meters,
  landing the pole at **lat/lon (0, 0)** at true physical size (a 608 km patch —
  roughly France; k = 1.00 at the pole → 1.07 at 60°S). Full resolution survives
  and exaggeration 1× is honest, but the cap looks tiny on a world map.
- **Angular rotated-pole** — a PROJ `ob_tran` warp
  (`+proj=ob_tran +o_proj=webmerc +o_lat_p=0 +o_lon_p=180`) rotates the Moon so
  the south pole sits at null island, then draws **1 lunar degree as 1 Earth
  degree**: the 80°S cap fills ±10° (~2,240 km). Chirality is preserved (pure
  180° rotation, no mirroring). Horizontal scale inflates by R⊕/R☾ ≈ 3.67 —
  set exaggeration ≈3.7× for true-ratio relief.
- **True-position** — `gdalwarp` with `PROJ_IGNORE_CELESTIAL_BODY=YES` maps lunar
  lon/lat onto Earth's mercator grid at its real coordinates. The global LDEM works
  this way (same ≈3.67× inflation and ≈3.7× exaggeration), but polar caps are
  clipped to the 80°→85.05°S ring: **Malapert at 86°S falls off the map edge**.
  Good for seeing extent in context; useless for the pole itself.

Assembly runs in CI (`.github/workflows/assemble-moon-lola.yml`): download from
PDS/PGDA, convert with GDAL, publish to a CORS + range-request host the geomatico
COG protocol can stream. Locally-converted files load through the custom terrain
source's local-file picker without any hosting.

## Dynamic strip streaming (`stacdem://`, WIP)

`lib/stacdem-protocol.ts` is the resolution-ladder skeleton: below a threshold
zoom it windows the base COG (whole-Moon views cost a few range requests thanks
to its overviews); above it, it discovers Kaguya TC DTM strips for the tile
bbox and warps them over the base. Discovery is two-tier: a **FlatGeobuf
tindex** (built by `.github/workflows/build-kaguya-tindex.yml`, schema after
`gdaltindex`/`pdal tindex` — `location` + footprint + a precomputed proj4 `srs`
column) that the browser bbox-queries *remotely* via HTTP range requests, with
**live STAC `/search`** as the no-index fallback and freshness path. Warping
uses [`geowarp`](https://github.com/GeoTIFF/geowarp) + proj4 — no hand-rolled
resampling. The same machinery pointed at the strips' `orthoimage_*` assets
gives a matched imagery basemap that sharpens in lockstep with the terrain.

### Index vs data, terrain vs imagery — the cheat-sheet

The FlatGeobuf is a *catalog*, the COGs are the *data*: every high-zoom tile
request first asks the index (remote-FGB bbox query or live STAC search)
"**which strips** touch this bbox?", then range-reads "**which pixels**" from
the returned COGs. Four roles, four sources:

| Role | Source | Form |
|---|---|---|
| Terrain base (low zoom) | LOLA global + PGDA polar caps | repacked COGs (HF) |
| Terrain detail (high zoom) | Kaguya TC DTM strips | USGS COGs, live-warped |
| Imagery basemap (global) | OPM moon hillshade (CARTO XYZ, alive) or USGS WMS via titiler | ready-made tiles |
| Imagery detail | the strips' `orthoimage_*` COGs | deck.gl-raster candidate |

Only the **terrain base** row needs repacking, for three independent reasons:
PGDA sends no CORS headers, the CRS is lunar (the geomatico protocol is
hard-wired EPSG:3857), and the global GDR rasters aren't COGs at all (untiled,
no overviews). The Kaguya strips need none of that — already CORS-served COGs —
only the client-side warp.

**geowarp vs deck.gl-raster is a tier choice, not a rivalry.**
[`geowarp`](https://github.com/GeoTIFF/geowarp) is CPU, explicit, and returns
*data* (a `Float32Array` we can terrarium-encode → usable for maplibre
**terrain**); its custom `forward`/`inverse` hooks take plain proj4 converters,
so lunar CRSes unknown to any EPSG registry just work. deck.gl-raster
reprojects on the **GPU** and outputs pixels-on-screen — faster and prettier,
but unusable for `setTerrain`, so it only competes for the **imagery** rows.

**Is there an existing lunar DTM basemap to skip all this?** No — that gap is
the project. What's hosted today is colorized renders (USGS WMS, Trek, OPM —
pictures of terrain, not elevations), wrong formats (raw GDR grids, JP2), a
mesh encoding maplibre can't eat (Cesium ion's Moon quantized-mesh — real
streamable lunar terrain, what the Cesium demos use), or CORS-less COGs (PGDA).
Nobody serves lunar elevation as terrarium/terrain-RGB tiles or
mercator-labeled COGs; the repacked set here appears to be the first
browser-streamable lunar DEM for the MapLibre world.

### deck.gl-raster for the basemap side

An alternative under evaluation is
[`@developmentseed/deck.gl-raster`](https://github.com/developmentseed/deck.gl-raster)
(the maintained successor of kylebarron/deck.gl-raster) via a deck.gl
`MapboxOverlay`: its `MosaicLayer` is viewport-driven — per-source rendering
that the FlatGeobuf tindex could feed directly — and `MultiCOGLayer` unifies
parallel COGs (caveat: assumes one shared CRS across sources). Timing caveats
from upstream issues: the high-level STAC layer is
[unbuilt (#147)](https://github.com/developmentseed/deck.gl-raster/issues/147),
and the MultiCOG API is being
[revamped (#417)](https://github.com/developmentseed/deck.gl-raster/issues/417)
around the RasterTileLayer refactor (#404) — prototype behind a flag, don't
couple deeply yet. Hard boundary either way: deck.gl layers can't feed
maplibre's terrain engine, so elevation stays on `stacdem://`; deck.gl-raster
only competes for the imagery/basemap layer.
