name: qgis-plugin-gotchas-0-12
description: QGIS plugin facts found in the 0.12.x rounds - the folder renamed to iconem_terrain_viewer in 0.12.1 (a same-id plugin on plugins.qgis.org), what kept the terrain_viewer prefix, the experimental setting's key, no URL scheme, no native PMTiles reader in QGIS (GDAL only) and Overture's host refusing GDAL, the 3.44 exit crashes explained (the tests' teardown, QGIS never finalizes Python), compact GeoJSON

Found on 2026-11-27 while building Terrain Viewer 0.12.0 (QGIS 4.2 and 3.44, Windows).

- **The plugin's folder is `iconem_terrain_viewer` since 0.12.1** (2026-11-27; it was `terrain_viewer`). plugins.qgis.org has another plugin with the folder `terrain_viewer` (Terrain Viewer by LiDARgeek, 1.3.1, QGIS 3.40 to 3.99), and QGIS merges plugins by folder name across repositories (the part of `file_name` before the first dot), the last repository read winning (`pyplugin_installer/installer_data.py`, `rebuild`): in QGIS 3.40+ the Plugin Manager showed theirs in place of ours and `installPlugin("terrain_viewer")` installed theirs. The display name is never the key, so it stays "Terrain Viewer". **Kept on purpose:** the QGIS settings (`terrain_viewer/<key>`), the layers' custom properties (`terrain_viewer/...`), the project scope `terrain_viewer` and the profile's data folder (`<profile>/terrain_viewer/`): renaming them would lose settings and frozen layers, and the other plugin (1.3.1 source read) stores none of these. **No migration code** (the maintainer's decision): an install of 0.12.0 or earlier is uninstalled by hand, and its panel finds no `terrain_viewer` entry in `plugins.xml`, so it offers nothing. **How to apply:** install paths are `%APPDATA%\QGIS\QGIS3\profiles\default\python\plugins\iconem_terrain_viewer` and the same under `QGIS4`; the profile's ini enables it as `iconem_terrain_viewer=true` under `[PythonPlugins]`; `updates.PLUGIN` must equal the folder name (the zip's top folder, the key in `plugins.xml`, `reloadPlugin`).
- **"Show also Experimental Plugins"** is `plugin-manager/allow-experimental` (`[plugin-manager]` in the profile's ini) in QGIS 3.44 and 4.2. `app/plugin_installer/allowExperimental` is the old key, read by neither. The checkbox's own state is also kept under `[QgsCollapsibleGroupBox] QgsPluginManagerBase\ckbExperimental\checked`.
- **QGIS registers no URL scheme** on any platform (no `x-scheme-handler`, no `CFBundleURLSchemes`, no Windows protocol key): nothing a web link can do to add a repository. The console one-liner (set `app/plugin_repositories/<name>/url`, then `pyplugin_installer.instance().reloadAndExportData()`) is verified in both versions.
- **Overture's tile host answers HTTP 400 to GDAL's `/vsicurl/`** (its HEAD, and a GET without a Range): its PMTiles cannot be an OGR layer. The plugin serves them as vector tiles from its own 127.0.0.1 server (`live/server.py` `/pmtiles/{z}/{x}/{y}.pbf`). `use_head=no` and `CPL_VSIL_CURL_USE_HEAD=NO` end on the same 400 (GDAL then sends a GET without a range); the S3 bucket behind the host answers 404 for current releases. Other https PMTiles work through GDAL with `|option:ZOOM_LEVEL_AUTO=YES`.
- **QGIS has no PMTiles reader of its own, on disk or remote** (checked 2026-11-27 in 3.44.11 and 4.2.0; an earlier note here said "from disk only", which was wrong). `QgsVectorTileLayer("type=pmtiles&url=...")` is invalid with no provider; the vector tile providers are xyzvectortiles, mbtilesvectortiles, vtpkvectortiles, arcgisvectortileservice; the word pmtiles is not in qgis_core.dll; QGIS's source names PMTiles only in the STAC browser (4.4+, PR 67708), which opens it as `/vsicurl/...|option:ZOOM_LEVEL_AUTO=YES` with ogr. "QGIS reads remote PMTiles" means GDAL's driver (GDAL 3.8+), which is the plugin's route. Where GDAL lacks the driver (`ogr.GetDriverByName("PMTiles")` is None), 0.12.2 serves every archive from the plugin's server (`vector_library.GDAL_PMTILES`; `test_overlays_live.py --no-gdal-pmtiles`). No QGIS 3.28 on this machine (the folders under Program Files are empty stubs): that path is not run on a real old GDAL.
- **Compact GeoJSON** (`format: "compact"`, UNESCO's components since 2026-11-27): GDAL reads the file as written (fields n, r, i), so the layer had no category. `vector_library.expand_compact` is the app's `expandCompactGeoJSON`; the full file is written to `<profile>/terrain_viewer/vector/<id>.geojson` and opened from there. `make_app_defaults.py` must carry any new entry field the plugin reads (`format` was missing from `VECTOR_FIELDS`).
- **Never call `featureCount()` on a planet PMTiles layer** (it reads everything: a test hung on VIDA's 2.7 billion footprints).
- **The access violation QGIS 3.44 ended `test_setup_live.py` and `test_live.py` with after their "OK"** (0xC0000005, no Python frame, about one run in four) **was the scripts' teardown, not the plugin. Solved 2026-11-27 (0.12.2).** They called `app.exitQgis()` (which destroys GDAL's drivers) and then `sys.exit()`, whose interpreter shutdown deleted the script's `QgsMapCanvas` (its last render job holding a raster layer) or an `osgeo` dataset after GDAL: a call to address 0 from gdal313.dll inside `Py_FinalizeEx`. **QGIS itself never finalizes Python** (`QgsPythonUtilsImpl::exitPython`: `// causes segfault! //Py_Finalize();`) and deletes its canvases before `exitQgis()` (`QgisApp::~QgisApp`), so a plugin's Python objects are never deleted at quit. **How to apply:** every `test_*.py` ends with `test_teardown.leave(app, code, dock, bridge, canvas)` (widgets deleted, `exitQgis()`, exit functions, `os._exit`); never write `app.exitQgis(); sys.exit()` in a new test. `TV_TEARDOWN=old` reproduces the crash. **How it was found:** faulthandler says nothing useful ("no Python frame"); a ctypes vectored exception handler (`AddVectoredExceptionHandler`, its callback and everything it touches kept alive with `Py_IncRef`) that scans the faulting thread's stack from `CONTEXT.Rsp` and names each word's module and nearest export (`dbghelp` `SymFromAddr`) gave the chain in one crashing run. `RtlCaptureStackBackTrace` alone only shows the handler's own stack when the fault is a call to 0. The earlier attempts listed here before (pool joins, timers, task waits, a 4 s wait) changed timing only.
- **The Python backend's request threads use GDAL** (building shadows: MVT decode, rasterize). `LiveServer.stop()` waits for them (`HANDLER_GRACE_S`, 2 s) since 0.12.2, after the pools; QGIS unloads plugins at close (`saveWindowState` > `unloadAll`) before it destroys GDAL.
- **`QgsDataSourceUri.setParam` adds, it does not replace**: `removeParam` first when rewriting `url`.
- **A `.qlr` rewrites XYZ addresses** (adds `crs=` and `format`): compare layers by their `url` parameter, not by `source()`. Memory layers lose their features in a `.qlr`: write them to a GeoPackage first (`setups.py`).
- **Test launches fail with `MemoryError` or empty output when the machine's commit memory is exhausted** (another application): retry, it is not the code.
